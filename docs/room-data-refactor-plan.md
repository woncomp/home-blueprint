# 房间数据结构改造计划

日期：2026-10-27  
状态：已实施（174 项测试通过，浏览器冒烟验证完成）

## 一、目标结构

将目前分离的 `roomNames`、`roomLabelPos` 合并为 `rooms`：

```json
"rooms": {
  "w1|w2|w3|w4": {
    "name": "客厅",
    "offsetx": 0.1,
    "offsety": -0.05
  }
}
```

保留两个偏移字段，以支持现有的标签横向、纵向拖动能力。

同时明确数据边界：

- `rooms` 只保存用户可编辑的信息：名称、标签偏移。
- 房间面积、顶点、墙面归属仍由 `walls` 实时计算，不重复持久化。
- `roomNameHints` 继续保留，作为全局默认命名规则。
- 删除旧的 `roomNames` 和 `roomLabelPos`。
- 数据版本从 `3` 升级为 `4`。

## 二、房间键的生成规则

不要简单使用坐标，也不要依赖墙数组顺序。按以下方式生成：

1. `detectRooms()` 遍历房间边界环时，同步收集经过的**原始墙 ID**。
2. 不使用 `w1#0` 之类的派生墙段 ID。
3. 对墙 ID 序列做循环起点、正反向规范化，再用 `|` 连接：

   ```text
   w1|w2|w3|w4
   ```

4. 将 `room.key`、`faceNav.faceKeys`、`segRooms.left/right` 全部切换为这种键。

这样，移动墙身、调整墙长或拖动端点时，只要围墙关系没变，房间键就不会变，名称和标签位置也不会失效。

需要额外加入**键冲突检测**：如果不同房间意外生成完全相同的围墙序列，不能静默覆盖数据；异常情况可使用 `#2` 等后缀消歧并输出警告。

## 三、标签偏移的定义

将 `offsetx/offsety` 定义为：

> 相对房间默认标签锚点（多边形质心）的偏移，以房间包围盒宽度、高度为单位。

例如：

```json
"offsetx": 0.1
```

表示从默认位置向右移动包围盒宽度的 10%，不是移动 0.1 米。

计算方式：

```js
labelX = centroidX + offsetx * bboxWidth;
labelZ = centroidZ + offsety * bboxDepth;
```

旧数据 `[u, v]` 按以下方式迁移：

```js
offsetx = u - centroidU;
offsety = v - centroidV;
```

缺省值均为 `0`，因此未调整过标签的房间仍显示在质心。右侧面板和拖动交互可以继续展示原来的 `0～1` 位置，只在读写持久化数据时转换，减少界面改动。

## 四、实施步骤

### 1. 改造房间检测与键生成

涉及 `js/model.js`：

- 在面环遍历中记录边界墙 ID。
- 新增墙 ID 序列规范化函数。
- 给运行时 `room` 增加 `wallIds`。
- 将 `room.key` 切换为墙 ID 键。
- 保留旧坐标键生成能力，专供旧数据迁移使用。
- 检查墙面两侧归属、面环导航是否正常工作。

### 2. 合并数据并增加 v3 → v4 迁移

涉及 `createEmptyData()`、`normalizeData()`、`validateData()`：

- 新数据默认生成 `rooms: {}`。
- 根据当前墙体重新检测房间，建立“旧坐标键 → 新墙 ID 键”的映射。
- 合并有效的 `roomNames[oldKey]` 和 `roomLabelPos[oldKey]`。
- 自动丢弃已经失效的旧记录。
- 删除旧字段，保留 `roomNameHints`。
- 校验 `rooms` 必须为对象，`name` 必须为字符串，偏移必须为有限数值。
- 保证重复加载、重复迁移是幂等的。

### 3. 统一房间数据访问入口

把名称解析、标签定位和记录读写收敛到同一组辅助函数：

```js
getRoomRecord(data, roomKey)
resolveRoomNames(data, rooms)
roomLabelPoint(room, data)
roomLabelUV(room, data)
reconcileRooms(data, previousRooms, currentRooms)
```

避免 2D、3D、右侧面板分别直接操作 `data.rooms[key]`，造成字段遗漏。

### 4. 改造界面读写

- `panel.js`：名称和位置都写入同一个 `rooms[key]` 记录；清空名称只删除 `name`，不要误删标签偏移。
- `plan2d.js`：标签拖动、Esc 还原、面板位置编辑统一使用新结构。
- `scene3d.js`：名称和标签位置改从 `rooms` 读取。
- JSON 查看、应用和导出统一使用 v4 结构。

### 5. 处理增删墙后的数据继承

墙 ID 键能解决几何移动，但增删墙仍会改变键，因此需要明确策略：

- **完全相同的键**：直接保留记录。
- **唯一且明确的围墙交集匹配**：继承原名称和偏移。
- **无法唯一判断**：不猜测，重新使用默认名称。
- **已消失的房间**：删除对应记录。
- **每次户型编辑提交后执行清理**，不要等 JSON 膨胀后再手工处理。

## 五、测试与验收

重点补充以下测试：

1. 墙数组顺序、边界遍历方向改变时，房间键保持一致。
2. 移动墙、修改墙长、拖动端点后，名称和偏移不丢失。
3. 多房间、T 型、X 型连接下，墙面左右房间归属正确。
4. v3 数据能正确合并名称与标签位置，失效旧记录被清理。
5. v4 JSON 导入导出后数据保持一致，不再出现旧字段。
6. 2D、3D、右侧面板显示相同的名称和位置。
7. 标签拖动、Esc 还原、清空名称互不破坏其他房间信息。
8. 增删墙、房间拆分与合并符合既定的数据继承策略。
9. 异常重复键不会导致房间信息被静默覆盖。

最终验收标准：**移动墙体不再产生重复房间记录，当前户型每个房间最多只有一条 `rooms` 记录，旧 JSON 可以无损迁移有效信息。**

目前项目已有 5 项墙面几何测试失败，实施前应先记录这个基线；本需求至少保证新增测试全部通过，且不引入新的失败。
