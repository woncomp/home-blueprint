# 房间 ID 改用必要围墙环：实施计划

日期：2026-10-27  
状态：待实施  
改造前基线：`node --test tests/*.test.mjs` 共 180 项测试全部通过。

## 一、问题与目标

当前 `detectRooms()` 把房间完整面环经过的所有原始墙 ID 交给 `canonicalWallKey()`，因此房间键包含：

- 被 T/X 接点切开后多次出现的同一面墙；
- 在面环上往返经过的死端短墙；
- 绕过室内凹口、封闭子房间时经过的附加墙。

默认户型客厅就是一个典型例子。其完整面环包含 `w1～w6、w16、w17`，但构成其最简外部闭环的必要墙只有：

```text
w1|w2|w3|w4
```

本需求只改变**房间标识所使用的墙集合**，不改变房间本身的几何与拓扑含义：

- `points`、`area`、真实地面形状不变；
- `segRooms`、`faceNav`、逻辑墙段和相邻墙导航不变；
- 墙面展开、电气节点归属、线路和 3D 渲染不变；
- 已保存的房间名称与标签偏移必须迁移到新键。

## 二、现状与根因

关键代码位于 `js/model.js`：

1. `detectRooms()` 在面遍历时生成 `faceWallIds[i]`，记录完整面环的原始墙 ID。
2. 当前键生成直接执行：

   ```js
   canonicalWallKey(faceWallIds[i])
   ```

3. `canonicalWallKey()` 只合并**相邻重复**墙 ID，并规范化循环起点和正反向；它不会判断某面墙是否为闭合房间所必需。
4. `rooms` 以该键持久化用户数据，且 `reconcileRooms()`、`resolveRoomNames()`、2D/3D 和面板都依赖同一个 `room.key`。

因此不能只在 `canonicalWallKey()` 中做全局 `Set` 去重。全局去重仍会保留 `w5/w6/w16/w17`，还会丢失墙环顺序，无法表达“必要围墙环”。

## 三、“必要墙”的判定定义

将必要墙定义为：

> 在当前平面墙图中，能够包围目标房间区域的稳定最简外闭环上的原始墙。完整面环上的内部往返支路不参与；如果填入相邻房间能得到更简的外部闭环，则使用简化后的外闭环生成 ID。

“更简”使用确定性的字典序比较：

1. **不同原始墙 ID 数量更少者优先**；
2. 数量相同时，**闭环中心线总长度更短者优先**；
3. 仍相同时，以规范化墙键字典序决定，保证结果不依赖遍历顺序。

这个顺序有两个重要作用：

- 默认客厅绕过卧室 A 的环有 6 类墙，填平卧室 A 后只有 4 类墙，因此采用 `w1|w2|w3|w4`。
- 普通贯通隔墙分出的左右房间，各自闭环和整套外圈可能都为 4 面墙；整套外圈更长，不能因此把真正的分隔壁从两个房间的 ID 中去掉。

这里求的是适合家庭户型规模的**局部稳定最简环**，不枚举所有房间子集做指数级全局组合优化。

## 四、推荐实现：基于面集合求外边界并逐步约简

### 4.1 保留两套墙序列

在 `detectRooms()` 的运行时结果中明确区分：

- `room.wallIds`：继续保存真实完整面环的原始墙 ID，供现有继承逻辑和诊断使用；
- `room.keyWallIds`：新增，保存用于生成键的必要墙 ID 环序列；
- `room.key`：由 `canonicalWallKey(room.keyWallIds)` 生成。

不要把 `room.wallIds` 直接改成必要墙集合，否则会改变 `reconcileRooms()` 对真实房间拆分、合并和相邻关系的判断依据。

### 4.2 用原子边两侧的面归属计算区域边界

现有面遍历已经有实现所需的全部信息：

- `edgeInfos`：原子边及其原始 `wallId`；
- `halfFace`：每条有向半边所属的面；
- 顶点坐标和角度顺序：用于重新遍历边界环；
- `exteriorIdx` 和房间面积过滤结果：用于排除外平面、微面。

对一个房间面集合 `S`，原子边属于区域边界的条件是：

```text
左侧面的“是否属于 S” !== 右侧面的“是否属于 S”
```

也就是只保留恰好一侧在 `S` 内的原子边。由此自然得到：

- 两侧都属于同一房间面的死端短墙不会进入边界，不需要通过“ID 出现两次”猜测；
- 两个已合并房间之间的隔墙不会进入外边界；
- 原始墙只部分属于边界时仍以原子边参与几何闭环，最终再映射回原始墙 ID；
- 如果边界含内孔环，取包围区域的外环作为键来源，内孔墙不进入 ID。

为便于实现和测试，建议把该过程提成 `detectRooms()` 内部的纯辅助步骤，而不是把规则散进 `canonicalWallKey()`。

### 4.3 从单个房间开始局部合并

对每个有效房间面分别计算，初始 `S = { targetFaceIndex }`：

1. 计算 `S` 的外边界环及其评分 `(不同原始墙数, 环长, 规范化墙键)`。
2. 找出与 `S` 至少共享一条原子边的其他有效房间面。
3. 分别模拟把其中一个相邻面加入 `S`，重新计算外边界和评分。
4. 只接受评分严格优于当前环的候选；多个候选时按同一评分规则选最优，再以面序号作最终确定性兜底。
5. 接受后重复上述过程，直到没有更优候选。最终外环上的原始墙 ID 即 `keyWallIds`。

伪代码：

```js
let region = new Set([targetFace]);
let current = outerWallRing(region);

while (true) {
  const candidates = adjacentRoomFaces(region)
    .map(face => outerWallRing(new Set([...region, face])))
    .filter(candidate => isBetter(candidate, current));
  if (!candidates.length) break;
  const best = chooseDeterministically(candidates);
  region = best.region;
  current = best.ring;
}

return current.wallIds;
```

所有房间的旧键、新键应在同一次面检测中先完整算出，再统一调用 `assignRoomKeys()`。计算某个房间的必要环时，不依赖正在生成的新房间键，避免循环依赖。

### 4.4 为什么不做这些简化处理

- **只做 `new Set(room.wallIds)`**：仍会包含内部墙，且没有环顺序。
- **只删除重复 ID**：无法删除只出现一次的 `w5/w6`，也无法可靠识别所有死端支路。
- **只保留邻接外平面的墙**：内部房间会丢失真正的分隔壁，甚至只剩两面外墙。
- **直接修改真实面环**：会误改房间面积、墙面左右归属和三墙导航，影响范围远超 ID 需求。
- **使用凸包**：会把真实的 L 形、凹形房间错误简化，且凸包边未必是实际墙体。

## 五、数据版本与旧键迁移

### 5.1 升级到 version 5

房间键是 `rooms` 的持久化主键。改变生成规则后必须升级数据版本，不能让旧 v4 文件静默丢名：

- `createEmptyData()` 生成 `version: 5`；
- `validateData()` 接受 v5；
- `normalizeData()` 在现有 v3→v4 后增加 v4→v5；
- v1/v2/v3 数据继续按原顺序逐级迁移到 v5；
- `data/default.json` 迁移为 v5，客厅记录改为新键，其余名称和偏移保留。

### 5.2 在同一次检测结果中保留旧键用于迁移

迁移时必须知道“同一个面”的旧键和新键，不能仅按墙集合模糊匹配。建议让运行时 `room` 额外提供仅供迁移使用的 `legacyKey`：

- `legacyKey`：按旧规则 `assignRoomKeys(canonicalWallKey(faceWallIds))` 得到；
- `key`：按必要墙环生成并消歧得到；
- 两者按面一一对应，包括异常重复键的 `#2/#3` 后缀。

`migrateRoomsV4toV5(data)` 按该对应关系复制记录：

```text
data.rooms[room.legacyKey] → 新 rooms[room.key]
```

迁移时重新建立 `rooms` 对象，只复制当前仍存在的房间；名称、`offsetx`、`offsety` 原样保留，失效旧记录删除。若异常数据导致多条旧记录争用同一目标，不得静默覆盖，应按面顺序确定性保留并输出告警。

`legacyKey` 只服务于 v4→v5 迁移，不进入持久化 JSON，也不参与日常界面逻辑。v5 再次加载不得重复迁移，保证幂等。

### 5.3 户型编辑后的继承

`reconcileRooms()` 继续以真实 `room.wallIds` 计算围墙交集，不改用 `keyWallIds`：

- 必要墙未变时，新键相同，名称和偏移直接保留；
- 新增/删除死端短墙或可填平的内部房间时，键现在可以保持不变，不再需要“继承”；
- 真正拆分、合并房间时仍沿用现有“一对多、多对一不猜测”的策略；
- 已消失房间仍清理，重复键仍由 `assignRoomKeys()` 消歧。

## 七、测试计划

### 7.1 必要墙环核心用例

1. **矩形 + 死端短墙**：键始终为 `w1|w2|w3|w4`，短墙不进入 `keyWallIds`。
2. **默认客厅**：新键严格等于 `w1|w2|w3|w4`；`w5/w6/w16/w17` 不参与。
3. **默认其他房间**：每个检测房间恰有一个 `rooms` 记录，没有遗留旧键或丢失名称、偏移。
4. **普通 T 型两房间**：两个键仍不同，真正的贯通分隔壁仍保留，不能都被简化成同一个外圈键。
5. **X 型四房间**：四个键互不相同，墙面两侧归属不变。
6. **真实 L 形单房间**：保留构成凹形的实际墙，不按凸包或最少四面墙误删。
7. **完全封闭的内部房间**：外部房间 ID 不包含内部房间墙；内部房间仍使用自己的完整闭环。
8. **稳定性**：墙数组顺序、墙 start/end 方向、面发现顺序变化时键一致；移动墙身、调墙长、拖端点且拓扑不变时键不变。
9. **异常冲突**：不同面生成相同基础键时仍追加 `#2/#3`，不得覆盖房间数据。

### 7.2 不影响现有拓扑和渲染的回归

- 同一输入在改造前后的 `points`、`area`、真实 `wallIds` 一致；
- `segRooms.left/right` 与新 `room.key` 对应当前房间；
- 默认客厅三墙展开仍绕过实际面环和两根死端短墙，不能被“必要墙环”截断；
- `buildWallSegments()`、`buildFaceRanges()`、`adjacentWallViews()` 现有测试全部保留；
- 2D/3D 房间面积、标签位置和选中行为不变。

### 7.3 迁移与继承

- v4 默认户型迁移后，客厅“名称=客厅”准确落到新键；
- 带 `offsetx/offsety` 的 v4 房间完整保留偏移；
- v1/v2/v3 输入最终均得到 v5，旧迁移能力不回退；
- v5 重复解析幂等，不产生 `legacyKey` 等持久化字段；
- 失效房间旧记录被清理，异常映射冲突不静默覆盖；
- 新增/删除内部短墙时键不变且记录原样保留；
- 真实房间拆分、合并仍不跨房间猜名。

## 八、验收标准

1. 默认客厅 ID 为 `w1|w2|w3|w4`。
2. 内部短墙、可填平的子房间凹口不再无意义地扩大房间 ID；真实分隔壁不会被误删。
3. 旧 JSON 中的有效房间名称和标签偏移无损迁移。
4. 房间真实几何、面积、墙面归属和邻墙导航不变。
5. 全量自动化测试通过，默认户型浏览器冒烟通过。
